# Справка по DO Checker

## Основные разделы

### 1. Main Checker

Основная страница для запуска проверок.

* **URL(s)**: один или несколько сайтов, каждый с новой строки.
  Схему можно не писать — без неё подставляется `http://`,
  а редиректы на HTTPS отслеживаются и попадают в лог результата.
* **Country**: страна выходного узла, обязательна.
  Вариант **ALL** (в начале списка) означает «каждый сайт в каждой стране из
  geo-каталога» — это тот же механизм, что и на странице Multi-Geo.
  Регион, город и ISP в текущей версии выбрать нельзя:
  на enterprise-тарифе API для получения этих значений [пока] недоступен.
* **Proxy Settings**:
    * `Network`: тип сети выходного узла — residential, mobile или оба.
      Обязателен.
    * `Proxy service`: через какой сервис проверять.
      Сейчас доступен только SOAX.
    * `Transport`:
      HTTP или SOCKS5. Один и тот же сайт через SOAX может отвечать по-разному
      по HTTP и по SOCKS5,
      поэтому проверка по одному транспорту ничего не говорит про другой.
      Предвыбранное значение берётся из `soax.transport` в `app.yaml`;
      если эта переменная не задана, транспорт нужно выбрать явно —
      прогон без него не запустится.
    * `DNS resolve`: где резолвится имя проверяемого сайта.
      `on exit node` (по умолчанию) — на выходном узле,
      то есть «как у пользователя в этой стране».
      `local` — через локальный DNS.
* **Advanced / Overrides**:
    * `Timeout (sec)`: сколько ждать ответ сайта.
    * `Screenshot`: снимать ли скриншот страницы.
      Скриншот снимается через тот же транспорт и ту же сессию,
      что и сама проверка, то есть с того же выходного узла.
      Если при SOCKS5-прогоне снять его через SOCKS5 не удалось,
      он снимается по HTTP, и это отображается в логе результата.
    * `Debug Mode`: добавляет в лог результата техническую секцию —
      строку подключения без пароля, отправленные заголовки,
      ответ предварительной проверки.
    * `Proxy Host` и `Proxy Port` показаны неактивными:
      адрес шлюза задаётся в `.env`, а не на странице.

Перед каждым прогоном приложение делает краткую проверку,
жив ли прокси-сервис:
несколько запросов к сторонним сайтам через тот же шлюз.
Если сервис недоступен, прогон не начинается и приложение об этом сообщает,
иначе отчёт выглядел бы как «все зеркала недоступны».
Отключается ключом `alive_check.enabled` в `app.yaml`.

Во время прогона кнопки `Run check`, `Clear logs` и `Reset Form` заблокированы.
Над блоком с результатами и под ним показана строка с итогами: сколько проверок,
доменов и стран в прогоне, а по завершении — сколько времени он занял.

Строки результата идут в том порядке, в каком введены домены, независимо от того,
какая проверка закончилась первой.

### 2. Multi-Geo Checker

Та же проверка, но страна указывается для каждой строки отдельно,
парами `домен код_страны`:

```
site1.org ca
site1.org az
site2.org tr
```

Строка с неверным форматом или невалидным кодом страны помечается ошибкой
по отдельности и остальной прогон не отменяет.

**N.B.**:
Форма **Multi-Geo Checker** принимает **любой** валидный/существующий (ISO
3166-1 alpha-2) код страны, даже тот,
которого нет в каталоге приложения (`data/catalog/soax_geo.json`).

### 3. Geo Catalog

Список стран, доступных в дропдауне на странице Checker, и в режиме ALL.
Хранится в `data/catalog/soax_geo.json`.

**Список ведётся руками.** Кнопка **"Refresh from SOAX (in background)"**
требует API-доступа, которого на enterprise-тарифе нет, и данных не принесёт.
Добавить или убрать страну можно формой «Manage Country List»:
ISO-2 коды в поле «Add new countries», затем **"Save List Changes"**.
Новая страна получает имя-заглушку, его можно поправить прямо в JSON.

При переносе на другую машину проще скопировать `soax_geo.json` целиком,
чем набирать список заново.

### 4. Settings

Прямое редактирование файла конфигурации `data/config/app.yaml`.

**Изменения вступают в силу только после перезапуска контейнера**
(`docker compose restart`).
Это касается и правок через эту страницу, и правок файла руками.
Страница показывает содержимое файла с диска, а сохранение записывает файл —
и всё; работающее приложение продолжает использовать те настройки, с которыми стартовало.

**Внимание!** Изменяйте настройки, только если понимаете,
что делаете (это касается, в основном, количества потоков и таймаутов).

Полезные опции:

* `default_theme`: тема по умолчанию (`auto`, `light`, `dark`).
* `http_client:custom_headers`: заголовки, добавляемые ко всем запросам проверки.
* `alive_check`: предварительная проверка доступности прокси — включение,
  список целей, сколько из них должно ответить.
* `soax.session_scope`: `task` — своя сессия на каждый сайт, `geo` —
  одна сессия на страну.

Невалидное значение приложение не остановит и не уронит:
при старте оно заменяется значением по умолчанию,
а наверху страниц появляется плашка с перечнем того, что было поправлено.
Пустой или испорченный файл означает запуск целиком на значениях по умолчанию
(тоже с плашкой).

Единственное, для чего нет дефолтного значения, — пароль пакета SOAX:
без него прогоны запрещены, и плашка явно сообщает об этом.
Пароль задаётся в `.env`, а не здесь: эта страница рендерится в браузер, и всё,
что в ней есть, попадает в скриншоты и в расшаренные сессии.

**Приоритет настроек**: значения из `.env` (например,
`APP_PORT`) имеют приоритет над значениями в `app.yaml`.

## Куда смотреть, если прогон повёл себя странно

Всё, что приложение делало, пишется в `logs/engine.log` — одним файлом и одним форматом,
причём каждая строка, относящаяся к проверке, несёт номер прогона и адрес сайта:

```
2026-10-17 13:43:50 [INFO] [pid=14] [run=ab12cd34ef56 url=example.com] engine: Task started.
```

Самое частое:

* **прогон не начался** — смотреть `grep -E "rejected|alive-check soax" logs/engine.log | tail`:
  там будет либо вердикт предварительной проверки прокси, либо причина отказа формы;
* **все зеркала недоступны** — почти всегда дело в прокси, а не в сайтах:
  `grep "gateway rejected" logs/engine.log | tail` покажет код ошибки шлюза;
* **нет скриншота при успешной проверке** — `grep "Screenshot failed" logs/engine.log | tail`;
* **в браузере ничего не появилось, а файлы на диске есть** — поток событий ушёл в другой
  воркер (`grep "No SSE queue" logs/engine.log`); на сам прогон это не влияет,
  результаты лежат в `logs/<дата>/<прогон>/`;
* **правка настроек не подействовала** — настройки читаются только при старте,
  нужен `docker compose restart`; с какими значениями работает процесс,
  видно в `grep -A11 "Configuration summary" logs/engine.log | tail -12`.

Подробнее — в `TROUBLESHOOTING.md` в корне репозитория: там рецепты на каждый случай и таблица
маркеров. Кнопка `Clear logs` удаляет папки прогонов, а логи самого приложения не трогает.
